# プロダクト構想(事業の正本)

最終更新: 2026-11-06

**この文書が正本として持つもの**: このプロダクトが何であり、なぜ作るのか。**持たないもの**——顧客セグメント、獲得チャネル、価格、工程表。**まだ何も決まっていないので書かない。** 技術の現在形は [data-model.md](data-model.md)、アーキテクチャ要件は [deliverable-architecture.md](deliverable-architecture.md)、現在地と次の一手は [HANDOFF.md](../HANDOFF.md)。

前身は [old/product-logo-management.md](old/product-logo-management.md)(2026-07-19・ロゴマネジメント起点)。2026-08-04 のピボット([deliverable-architecture.md §0.2](deliverable-architecture.md))が事業構想側に反映されないまま2か月動いていたので、ここで一本化した。

## 1. 前提

**生成AIによって、プロダクトを作れる機会が増える。** 作る側が増えれば、作ったものが見られ、使われるかどうかの側——Go-to-Market——に需要が移る。**そこに需要が出るはず**、というのがこのプロダクトの前提。

**これは前提であって、検証された市場ではない。** 誰にどう届けるかは決まっていない。

## 2. このプロダクトは何か

**2つのシステムでできている(2026-11-05 決定)。**

| | ブランドキット | ファクトリー |
|---|---|---|
| 向き | 帰納。サイト・資料・ロゴからブランドを抽出し、キットとして定義する | 演繹。キットを読んで成果物を出す |
| 最終出力 | **キットそのもの。** ロゴ・素材・ガイドライン・AI向けスキルを参照する、公開可能な1枚のまとめ(URL) | 動画・LP・バナーなど。キットから出た**作品の例** |
| 使い手 | 人と、URL を渡された外部の AI エージェント | この製品のハーネス/ワークフローで直接作る利用者 |

**本体はブランドキット。** 利用者はキットの URL を自分のエージェント(Claude Code・Claude Design など)に渡して作らせてもよいし、ファクトリーでこの製品上で作ってもよい。ファクトリーの成果物はキットの参照例であって、製品の中心ではない。

- **正本**: 「この会社・この事業について真であること」を、出典と確度付きで持つ。ロゴ・色・書体・声・実績。キットはその公開版。
- **読む口**: キットの URL は HTML(人向け)と `brand.md` / `tokens.json` / `tokens.css` / `logo.svg`(機械向け)を同じ住所で返す。

### 2.1 二重構造: ワークスペースは編集、公開版はその表側

ワークスペース(ログインの内側)のページは、**すべてが公開ページの下書き**で、1対1に対応する。ブランドキット・ロゴ・動画・素材集のどれも同じ。

- **公開はスナップショット。** 公開版は下書きに追随しない。再取り込みや編集で下書きが進むと「更新あり」になり、「更新を公開」で次の版が出る。前の版は残り、戻せる。Publication が Render(凍結した出力)を対象にする設計(§4.5)をそのまま使う
- **公開版に載るのは、測定された値と採用された値だけ。** 推定(モデルの読み)は載せない。ルールが測った事実(フッターのSNS・連絡先・言語。`confidence='evidenced'`)は採用と同じ扱いで載る。ワークスペースの仕事は、推定を採用に変えてから公開すること。推定が残っていても公開はブロックせず、警告で列挙する
- **ブランドキットは Take。** テンプレート `brand-kit`、ブリーフはプロファイルの凍結、公開 URL は `/k/[brandId]`(`canonical_slots` の `brand_guide` が Take を解決。`/p/[logoId]` と同じ型)。版ごとに Take が1つ。バニティ `/[handle]/[slug]` は層2として後から足す
- **調査の部品は編集の道具。** パイプラインバー・処理ログ・「まだわからない」の一覧・読み直しは、ページの中身ではなく編集の枠に置く。プレビュー=同じページから道具を外した表示。だからプレビューと公開版は定義上一致する
- **ブランドはワークスペース直下に並列。親子は属性。** `parent_brand_id` は「どのフォルダにいるか」ではなく**継承元**(2026-11-05)。サブブランドはそれ自体で完結した別のブランドで、親はその下に敷かれるアタッチメント: サブに無い項目だけ親の値が透けて見え、サブに値があればサブが勝つ(項目ごとの固定は今は無し。2026-11-06)。親を付けても何も複製されず、外しても何も消えない——親の層が見えなくなるだけ。公開済みのキットは公開時に解決した値を凍結しているので、親の付け外しは「更新あり」になるだけで公開版は変わらない。持ち物(Assets / Works)だけが入れ子になる。**メインブランドはワークスペースに1つ**(`organizations.main_brand_id`、migration 0061)。最初に登録したブランドが自動でなり、行メニューの「メインブランドにする」で付け替える。ツリーではメインに星が付くだけで、キットのページが「メインブランド」「{親} › サブブランド」と言う。語彙はメイン／サブ／独立で、「継承元」とは言わない(行メニューは「メインブランドにする」「サブブランドにする…」「サブブランドを追加」)。並び順は利用者が決める(`sort_order`、migration 0060)
- **語彙と位置を全ページで統一する。** 下書き / 公開中 / 更新あり / 非公開 を、ヘッダーの同じ場所に同じ語で。パイプラインの段の鮮度(緑/橙)とは別の軸なので、同じ見た目を使わない

**内部設計では正本が芯、UI ではキットと成果物が主役。** トップページでは URL ひとつ・ロゴひとつを「ポンと入れるだけ」でキットが立ち上がる——構造の精密さが入力負担に化けたら失敗([deliverable-architecture.md §1](deliverable-architecture.md))。

## 3. 「正本」を名乗れていない(2026-08-30 時点)

コードを照合した結果。**ここが企画と実装の最大のギャップ。**

| 主張 | 実際 |
|---|---|
| 正本がある | `brand_knowledge_claims` / `values` は稼働([0029](../supabase/migrations/0029_brand_knowledge.sql))。ただし**採用UIが無く `values` はほぼ空** |
| 成果物が正本から出る | **イベント動画だけ出ている。** `event-cm` はブランド知識から初期投影する([seed-from-brand.ts](../lib/templates/event-cm/seed-from-brand.ts))。`brief.kit` を焼き込んで描いていた旧LP(`campaign-lp`)と旧製品紹介動画は 2026-10-26 に CM Maker ごと削除した |
| 採用は人の明示操作 | **逆。** `values` を作っているのは URL 抽出の機械採用だけで、しかも見つからなくなった値を機械が DELETE する([lib/brand/import-assets.ts](../lib/brand/import-assets.ts))。`adopt_brand_knowledge`([0036](../supabase/migrations/0036_adopt_brand_knowledge.sql))は fact 層を出自に関係なく `confirmed` で刻む |
| 外部から読める | **読めない。** JSON を返す公開エンドポイントが1本も無い。到達できるのは `/p` `/c` `/v` の HTML/MP4 だけ |
| 外部組織が使える | **使える(2026-10-25)。** `/api/brands/**` 29本の門を `guardLabsRequest`(platform role)から [guardBrandRequest](../lib/brand-access.ts)(登録済みユーザーなら誰でも)に替えた。見える範囲はワークスペースの RLS が決める。「ブランドを追加」が呼ぶ生成の4本(`/api/labs/campaign/{generate,jobs,voice,video/[id]}`)も同じ門にした。Labs 権限が残るのはそれ以外の `/api/labs/**` と `/api/brands/backfill`(旧 Campaign Lab の移行)だけ |
| 本番で動く | LP 生成は detached job + ローカルFSで Vercel serverless では生きない。`captureSite`(Playwright)も動かず推定色になる |

## 4. 作る順序

前の節のギャップを埋める順。**日付は置かない。**

0. **CI**(`npm test` + `npm run docs:check` + lint/typecheck/build)。`.github/workflows` が無い。テスト48ファイルを回さずに正本の配線替えはしない
1. **ブランドキットの公開**(§2.1)。`brand-kit` Take、`/k/[brandId]` で HTML と `brand.md` / `tokens.json` / `tokens.css` / `logo.svg`、ワークスペースに公開ヘッダー(下書き/公開中/更新あり/非公開)と推定→採用の操作。`publications` をそのまま使う(Take にすれば `render_id not null` は満たせる)
2. **公開したキットで LP を作って確かめる。** 外部のエージェントに URL だけ渡して作らせ、キットに足りないもの(使い方の規則・素材の住所)を洗う。足りなかったものがキットの次の項目になる
3. **ロゴ・動画・素材集の公開を同じ語彙にそろえる。** ヘッダーの状態表示とツリーの点を共通部品にする
4. **採用UI の残り**。機械採用の格下げ、DELETE 廃止、`adopt` RPC の `source_kind → confidence` 写像
5. **field_path レジストリ**。実装の27パスに `mark.*`(クリアスペース・最小サイズ・禁止背景・反転条件)と `voice.*` を足す。`voice.* / audience.*` は `BrandTop.tsx` にラベルだけ存在し、書き手が無い
6. **外部組織が入れる門**。`guardLabsRequest` の解除範囲を実測。LP 生成を `run/[stage]` 方式へ
7. **法務6ページ**。`/company` `/contact` `/pricing` `/terms` `/privacy` `/legal/tokushoho` は**1つも存在しない**([components/SiteFooter.tsx](../components/SiteFooter.tsx) のリンク先が全部404)
8. その先: 課金、`brand_releases`、API キー(+ [lib/rate-limit.ts](../lib/rate-limit.ts) の分散化)、DTCG/SKILL.md、remote MCP、`file_extraction`、本番実行環境

**テンプレートは実案件が決める。** 受けた仕事の種類がテンプレートの種類になる。外部で作ったワークフローは [lib/templates/catalog.ts](../lib/templates/catalog.ts) に版固定で登録し、`remotion/kit/` の部品語彙へ寄せる。

## 5. 名前

**logos** 維持(小文字固定)。`SERVICE_NAME` / `SERVICE_TAGLINE` は [lib/config.ts](../lib/config.ts) の1箇所で変わる。

**最大の誤読リスクは「ロゴを作るツール」。** 由来(logotype = logos「言葉」+ typos「刻印」)を先に置く。「ロゴの前に、ロゴスがある。」/ *Before the logo, there is the logos.*

調べた事実:

- 米国第42類に Faithlife の文字商標「LOGOS」登録あり(Reg. 8115243、2026-01-27 登録。指定は聖書研究分野)。`logos` は英語でロゴの複数形なので、この分野では記述的と判断される可能性がある。**単独の文字商標ではなく結合商標**で出願する方が通りやすい
- 日本の「LOGOS」は株式会社ロゴスコーポレーション(アウトドア)が第9・11・21類に多数。第35・42類は未確認
- `logos.com` は Faithlife、`logos.ai` はデザイン系メディア、`logos.co` は別企業。`logos.design` / `logos.so` は未登録の可能性、`logos.dev` は 2026-10-13 満了
